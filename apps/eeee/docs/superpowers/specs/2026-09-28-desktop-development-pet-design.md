# 데스크톱 개발 펫 MVP 설계

**작성일:** 2026-09-28
**상태:** 대화형 설계 승인 완료, 구현 범위 확정
**프로젝트:** OSS Product Builder / Personal Development Orchestrator

## 1. 목적

이 프로젝트는 로컬 우선 방식의 데스크톱 개발 동료가 된다. 사용자가 작업하는 동안 작은 데스크톱 펫이 곁에 머물면서 오케스트레이터의 프로젝트 상태를 표정, 상태 메시지, 승인 요청으로 보여준다.

```text
사용자 요청 → 조사와 계획 → 명시적 승인 → 구현 → 검증 → 결과 보고
```

펫은 사용자의 화면을 몰래 감시하거나 자율적으로 컴퓨터를 조작하는 존재가 아니다. 프로젝트 상태를 보여주는 상태 기반 제어 화면이며, 안전 경계에서는 승인을 요청하고, 작업 결과는 검증 근거와 함께 보고한다.

## 2. MVP 목표

첫 번째 수직 기능 흐름에서 사용자는 다음을 할 수 있어야 한다.

1. Windows에서 데스크톱 펫을 실행한다.
2. 펫 패널에서 자연어 개발 요청을 입력한다.
3. 요청 분석 결과와 OSS 후보 비교 상태를 확인한다.
4. 펫 패널에서 후보 선택을 승인한다.
5. 작업 상태가 조사, 승인, 작업, 검증, 완료 또는 실패로 이동하는 것을 확인한다.
6. 결과 보고서와 프로젝트 workspace를 연다.

에이전트 어댑터를 구현하는 동안에는 결정론적인 가짜 작업 실행기를 사용해도 된다. 다만 상태 계약은 특정 에이전트 런타임에 종속되지 않아야 한다.

## 3. 사용자 경험

### 펫 화면

데스크톱 셸은 테두리 없는 투명 창으로 동작하며, 사용자가 드래그해서 위치를 옮길 수 있다. 캐릭터를 클릭하면 작은 동반자 패널이 열린다. 패널에는 현재 프로젝트, 작업 제목, 상태 메시지, 필요한 사용자 행동, 보고서와 workspace 링크가 표시된다.

첫 버전은 복잡한 애니메이션 시스템 대신 소수의 정적 이미지나 CSS 기반 표현을 사용한다. 캐릭터의 시각적 완성도가 Coordinator의 동작을 막아서는 안 된다.

### 상태 종류

Coordinator는 다음 상태 중 하나를 외부에 제공한다.

| 상태 | 의미 | 펫의 행동 |
| --- | --- | --- |
| `idle` | 진행 중인 작업이 없음 | 작업 시작 버튼 표시 |
| `researching` | 요청 분석 또는 OSS 근거 조사 중 | 진행 상태와 근거 수 표시 |
| `awaiting_approval` | 결정이나 위험한 작업에 사용자 승인이 필요함 | 승인 카드 표시, 승인 전에는 진행 중단 |
| `working` | 승인된 구현 작업 실행 중 | 현재 단계와 최근 이벤트 표시 |
| `verifying` | 결정론적인 검사 실행 중 | 테스트/빌드 진행 상태 표시 |
| `completed` | 검증 성공 | 보고서와 workspace 열기 표시 |
| `blocked` | 입력, 권한, 의존성 등이 부족함 | 막힌 이유와 해결 방법 표시 |
| `failed` | 근거가 기록된 작업 실패 | 실패 요약과 재시도/검토 표시 |

상태 전환의 주체는 Coordinator다. 데스크톱 셸은 상태를 렌더링하고 사용자 의도를 전달할 뿐, 로컬에서 상태를 추측하거나 임의로 변경하지 않는다.

## 4. 구조

```text
PySide6 데스크톱 셸
  - 투명한 펫 창
  - 동반자 패널
  - 상태 조회와 사용자 의도 전달
             |
             v
FastAPI 로컬 Coordinator
  - 프로젝트와 요청 API
  - 상태 전환 정책
  - 승인 경계
  - 작업과 이벤트 조정
             |
             v
SQLite 상태 저장소
  - 프로젝트 상태와 revision
  - 요청, 후보, 결정
  - 작업 이벤트, 검증 보고서, 산출물
             |
             +--> OSS 조사와 점수화
             +--> workspace/명령 정책
             +--> 에이전트 런타임 어댑터
             +--> 결정론적 검증
```

### 데스크톱 셸

첫 Windows 데스크톱 셸은 PySide6를 사용한다. 기존 Python 생태계를 유지하면서 투명하고 항상 표시되는 드래그 가능한 창을 빠르게 만들 수 있기 때문이다. 셸은 loopback HTTP를 통해 로컬 FastAPI 서비스와 통신하므로, 나중에 Tauri나 다른 클라이언트로 교체할 수 있다.

### Coordinator

Coordinator는 작업 상태를 전환하고, 승인을 저장하고, 실제 작업 실행을 허가하는 유일한 구성요소다. 기존 요청 planner와 approval service를 향후 workspace, agent, verification 어댑터와 조합한다.

상태를 변경하는 모든 동작은 append-only 이벤트를 남긴다. 이벤트에는 요청 또는 작업 ID, 주체(`user`, `coordinator`, `tool`), 동작, 결과, 관련 산출물 경로가 포함될 수 있다.

### 상태 저장소

UI 상태를 자유 형식 이벤트에만 저장하지 않고, 명시적인 project/task 상태 모델과 SQLite 테이블로 관리한다. 활성 작업은 반드시 특정 project revision을 가리킨다. 검증 결과에도 검사한 revision을 기록해서, 이전 상태의 검증 결과가 최신 상태를 완료 처리하지 못하게 한다.

## 5. 로컬 API 계약

첫 번째 클라이언트가 사용할 API는 다음과 같다.

- `POST /projects/{project_id}/requests`: 요청을 생성하고 task ID를 반환한다.
- `GET /projects/{project_id}/state`: 현재 펫 view model, 활성 작업, 필요한 행동, 최근 이벤트, 보고서 링크를 반환한다.
- `POST /projects/{project_id}/decisions/{request_id}/approve`: `ApprovalService`를 통해 후보 선택을 승인한다. `approved=True`를 직접 저장하는 경로는 계속 금지한다.
- `POST /projects/{project_id}/tasks/{task_id}/retry`: 재검증을 통과한 복구 가능한 `failed` 또는 `blocked` 작업만 재시도한다.
- `GET /projects/{project_id}/reports/{report_id}`: 저장된 검증/보고서 산출물의 메타데이터를 반환한다.

응답 view model은 UI용이지만 반드시 근거 기반이어야 한다.

```json
{
  "state": "awaiting_approval",
  "message": "OSS 시작점을 선택해 주세요",
  "task_id": "task-123",
  "required_action": "approve_selection",
  "candidates": [],
  "latest_event": {},
  "report": null
}
```

셸은 알 수 없는 상태나 필수 필드 누락을 조용히 무시하지 않고 `blocked`로 처리한다.

## 6. 안전 경계

- 셸은 shell command를 직접 실행하지 않는다.
- 후보 승인은 사용자의 명시적 행동이어야 하며 감사 이벤트와 함께 저장한다.
- workspace에 쓰기 전 canonical path 경계 검사를 통과해야 한다.
- 네트워크, 설치, 삭제, 외부 전송, 시스템 전역 작업은 각각의 권한 정책을 통과해야 한다.
- 첫 데스크톱 펫 단계에서는 배포, 메시지 전송, 결제, 삭제, 시스템 전역 변경을 다루지 않는다.
- 화면 캡처, 지속적인 화면 감시, 마이크 접근, 음성 제어는 범위에서 제외한다.
- 에이전트의 “완료했습니다” 메시지는 검증 근거가 아니다. Coordinator가 최신 project revision에서 결정론적인 검사를 다시 실행한다.

## 7. 구현 범위

이 설계는 데스크톱 펫 셸, 상태 view model, Coordinator와 API의 연결부를 다룬다. 첫 구현에서 모든 미래 어댑터를 완성할 필요는 없다.

### Milestone A: 보이는 상태 흐름

- 타입이 있는 project/task 상태 모델과 SQLite 저장 기능 추가
- 결정론적인 상태 머신을 제공하는 Coordinator 추가
- 최소 FastAPI 요청/상태 API 추가
- 상태를 렌더링하고 동반자 패널을 여는 PySide6 펫 창 추가
- 결정론적인 fake worker로 `idle → researching → awaiting_approval → completed/failed` 흐름 검증

### Milestone B: 실제 OSS 승인 흐름

- 기존 GitHub client와 scorer 연결
- 전체 후보 snapshot과 순서를 비교하도록 승인 검증 수정
- 후보의 근거, 위험, 승인 컨트롤을 패널에 표시

### Milestone C: 통제된 구현 흐름

- workspace 경계 검증과 명령 정책 강제
- protocol 뒤에 agent runtime adapter 추가
- revision을 인식하는 결정론적 검증과 보고서 산출물 추가

## 8. 검증 전략

다음 항목을 테스트한다.

- 유효한 상태 전환과 잘못된 상태 전환
- 프로세스 재시작 이후 상태와 이벤트 순서 복구
- 각 상태에 대한 UI view model 렌더링
- 작업 시작 전 승인 필수 여부
- workspace와 명령 정책의 거부 동작
- 오래된 revision의 검증 결과 거부
- 요청 생성부터 보고서 조회까지의 API 흐름

데스크톱 셸은 상태 렌더링과 사용자 의도 전달을 소수의 행동 테스트로 검증한다. 핵심 정책은 화면 서버 없이도 실행할 수 있는 순수 Python 테스트로 유지한다.

## 9. 첫 릴리스에서 하지 않는 것

- 상시 화면 이해
- 음성 중심 인터랙션
- 범용 자율 컴퓨터 사용 에이전트
- 다중 사용자 협업이나 원격 제어
- 자동 배포와 외부 커뮤니케이션
- 복잡한 3D 아바타나 캐릭터 마켓플레이스

## 10. 성공 기준

새로운 로컬 설치에서 펫을 실행하고, 요청을 입력하고, 승인 결정을 확인하고, 무승인 작업이 차단되는 것을 확인하고, 결정론적인 진행 상태를 보고, 최종 결과를 설명하는 보고서를 열 수 있어야 한다.

사용자는 애플리케이션 로그를 읽지 않아도 시스템이 무엇을 하고 있는지, 왜 대기 중인지 이해할 수 있어야 한다.
