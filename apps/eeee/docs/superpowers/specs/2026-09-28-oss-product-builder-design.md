# OSS Product Builder 설계 문서

- 작성일: 2026-09-28
- 상태: 설계 승인됨, 구현 전
- 범위: 사용자 요구사항을 분석하고 검증된 오픈소스를 선정·조립해 실행 가능한 개발 결과물을 만드는 개인용 개발 비서

## 1. 요약

OSS Product Builder는 사용자가 자연어로 원하는 결과물을 설명하면, 요구사항을 구조화하고, 후보 오픈소스를 조사·비교하고, 선택된 구성으로 프로젝트를 생성한 뒤, 코드 작성·설치·테스트·실행까지 수행하는 로컬 우선 개발 비서다.

디자인이 필요한 결과물은 구현 전에 오픈소스 레퍼런스와 사용자가 제공한 링크를 모아 `Reference Pack`으로 만들고, 레이아웃·컴포넌트·디자인 토큰·상호작용 패턴을 추출한다. 비서는 원본을 무단 복제하지 않고 출처·라이선스·변형 내역을 기록한 뒤, 선택된 레퍼런스를 바탕으로 시안과 실제 코드를 함께 만든다.

핵심은 “가장 최신인 프로젝트”를 무조건 선택하는 것이 아니라, 사용자 요구에 가장 잘 맞으면서 사용 규모·유지보수·보안·라이선스 측면에서 신뢰할 수 있는 구성요소를 선택하는 것이다. 비서는 선택 근거와 위험을 먼저 보여주고, 사용자가 승인한 작업만 환경에 반영한다.

첫 번째 결과물은 특정 채널에 종속되지 않는다. 로컬 웹 UI를 기본 인터페이스로 사용하고, 터미널·음성·Discord 등은 이후 어댑터로 추가할 수 있다.

## 2. 사용자와 성공 기준

### 대상 사용자

자신이 원하는 웹앱, 개발 도구, 자동화 프로그램, 로컬 AI 앱을 말로 설명하고, 검증된 오픈소스를 활용해 빠르게 결과물을 얻고 싶은 개인 개발자다.

### 대표 사용자 흐름

1. 사용자가 “개인 문서를 검색하고 요약하는 로컬 웹앱을 만들어줘”처럼 요구사항을 입력한다.
2. 비서가 목적·사용자·입력·출력·환경 제약을 구조화하고 부족한 정보를 질문한다.
3. 비서가 GitHub와 공식 문서를 중심으로 오픈소스 후보를 수집한다.
4. 후보별 요구사항 적합성, 사용 규모, 유지보수, 보안, 라이선스, 통합 난이도를 비교한다.
5. 디자인 요구가 있으면 오픈소스 UI·템플릿·제품 레퍼런스를 수집하고 Reference Pack을 만든다.
6. 선택안과 대안을 보여주고, 사용자가 구성과 설치를 승인한다.
7. 비서가 격리된 작업공간에서 프로젝트를 생성하고 의존성을 설치한다.
8. 비서가 기능 구현, 디자인 구현, 테스트, 빌드, 개발 서버 실행을 수행한다.
9. 하네스가 최신 프로젝트 상태를 기준으로 결정론적 검증과 독립 리뷰를 수행한다.
10. 비서가 변경 diff, 실행 결과, 테스트 결과, 사용한 오픈소스와 버전을 보고한다.

### 성공 기준

- 자연어 요구사항에서 실행 가능한 프로젝트 구조와 작업 목록을 만든다.
- 오픈소스 후보를 최소 2개 이상 비교하고 선정 근거를 남긴다.
- 설치 버전과 의존성 lockfile을 고정한다.
- 코드 변경 전후를 diff로 확인할 수 있다.
- 테스트·빌드·실행 결과를 확인한 뒤 결과물을 전달한다.
- 사용자의 승인 없이 외부 전송, 삭제, 배포, 구매, 시스템 전역 변경을 하지 않는다.

## 3. 제품 원칙

### 결과물 중심

대화의 목표는 그럴듯한 설명이 아니라 실행 가능한 프로젝트, 명확한 실행 방법, 검증 결과다.

### 적합성 우선

오픈소스 선정은 최신성보다 요구사항 적합성을 우선한다. GitHub stars는 adoption을 보여주는 보조 신호이며, 신뢰성의 단독 근거로 사용하지 않는다.

### 근거와 재현성

선정된 저장소 URL, 커밋 또는 버전, 라이선스, 조사 시점, 선택·탈락 이유를 기록한다. 생성된 프로젝트는 lockfile과 결정 기록을 포함한다.

### 승인 기반 실행

읽기와 계획은 자동화할 수 있지만, 쓰기·설치·네트워크·외부 시스템 변경은 권한 정책에 따라 승인받는다.

### 작은 성공부터

첫 실행 가능한 결과물을 빠르게 만든 뒤, 기능을 추가한다. 완전 자율적인 만능 에이전트와 지속적인 화면 감시는 초기 범위에 포함하지 않는다.

## 4. 제안 아키텍처

```text
사용자
  ↓
로컬 Web UI / CLI / 선택적 채널 어댑터
  ↓
요구사항 분석기 ── OSS 조사·평가 모듈
  ↓                         ↓
디자인 레퍼런스 에이전트 ── Reference Pack
  ↓
작업 계획·승인 관리자 ── OSS 결정 기록
  ↓
Coordinator Harness
  ├─ 역할별 에이전트
  ├─ 공유 프로젝트 상태
  ├─ 작업공간·파일 잠금
  └─ 검증·증거 수집
  ↓
권한 정책 계층
  ├─ 파일·Git
  ├─ 터미널·패키지 관리자
  ├─ 브라우저·문서 조사
  └─ 테스트·빌드·개발 서버
  ↓
격리된 작업공간
  ↓
검증기 → diff·로그·테스트·실행 결과 → 사용자
```

### 4.1 인터페이스 계층

기본 인터페이스는 로컬 웹 UI로 한다. 최소 화면은 다음 네 가지다.

- 요구사항 입력과 대화
- OSS 후보 비교와 승인
- 작업 계획·현재 단계·승인 요청
- 파일 diff, 로그, 테스트 결과, 실행 미리보기

인터페이스는 오케스트레이터 API에 연결하는 얇은 클라이언트로 유지한다. 따라서 이후 CLI, VS Code 확장, 음성, Discord를 추가해도 핵심 로직을 복제하지 않는다.

### 4.2 오케스트레이터

오케스트레이터는 요구사항을 `brief`, `constraints`, `acceptance_criteria`로 정규화하고, 조사·계획·실행·검증 단계를 상태 머신으로 관리한다.

각 실행은 다음 상태를 가진다.

`draft → researching → awaiting_selection → planned → awaiting_approval → executing → verifying → completed`

실패 시에는 `repairing` 상태로 제한된 재시도를 수행하고, 반복 실패나 권한 부족은 사용자에게 명시한다.

### 4.3 OSS 조사·평가 모듈

조사 모듈은 GitHub 저장소, 공식 문서, 릴리스 정보, 라이선스 파일, 보안 권고를 우선 사용한다. 검색 결과를 그대로 믿지 않고 후보의 원문 근거를 저장한다.

초기 점수 모델은 다음처럼 둔다.

| 평가 항목 | 가중치 | 평가 내용 |
| --- | ---: | --- |
| 요구사항 적합성 | 45 | 핵심 기능, API, 실행 환경, 확장성 |
| 사용·채택 신호 | 15 | stars, forks, dependents, 생태계, 실제 사용 사례 |
| 유지보수 | 15 | 최근 릴리스, 커밋 활동, 이슈·PR 대응 |
| 신뢰·보안 | 15 | 라이선스, 보안 이슈, 공급망 위험, 문서 품질 |
| 통합 비용 | 10 | 설치 난이도, 의존성, 현재 프로젝트와의 호환성 |

점수는 선택을 자동 확정하기 위한 값이 아니라, 후보를 비교하고 설명하기 위한 값이다. 점수가 높아도 핵심 제약을 위반하면 탈락시킨다.

조사 결과에는 다음을 포함한다.

- 후보 저장소와 공식 문서 링크
- 조사 시점과 선택한 버전 또는 커밋
- 위 평가 항목별 근거와 불확실성
- 라이선스와 보안 주의점
- 대체 후보와 탈락 이유
- 설치·운영에 필요한 외부 서비스와 비용

### 4.4 에이전트 런타임

에이전트 런타임은 직접 구현한 오케스트레이터와 분리된 어댑터로 둔다. 초기 후보는 다음과 같다.

- OpenHands SDK: 코드 작업과 격리된 작업공간 실행을 위한 기본 후보
- Open Interpreter 계열: 로컬 파일·터미널·작업공간 권한을 가진 대체 실행기
- Browser Use 계열: 브라우저 기반 조사와 검증이 필요한 작업의 선택적 어댑터

구체적인 런타임 선택은 구현 계획 단계에서 작은 프로토타입으로 검증한다. 런타임 교체가 가능하도록 `inspect`, `plan`, `edit`, `run`, `test`, `report` 작업 인터페이스를 공통화한다.

### 4.5 모델 라우팅

모든 작업에 가장 비싼 모델을 사용하지 않는다.

- 요구사항 분류·간단한 요약: 소형 또는 로컬 모델
- OSS 후보 비교: 검색 근거를 가진 중간 모델
- 복잡한 코드 수정·디버깅: 강한 모델
- 반복적인 테스트 실패 수정: 제한된 재시도와 동일 컨텍스트 재사용

LiteLLM 같은 모델 게이트웨이를 선택적 계층으로 두어 모델 라우팅, 요청별 비용, 예산과 실패 시 fallback을 관리한다. 모델과 가격 설정은 프로젝트 구성으로 고정하고, 결과 보고서에 사용량을 남긴다.

### 4.6 디자인 레퍼런스 에이전트

디자인 레퍼런스 에이전트는 사용자가 준 URL·스크린샷·키워드 또는 오픈소스 조사 결과에서 재사용 가능한 디자인 근거를 수집한다. 각 레퍼런스는 원본 URL, 저장소, 라이선스, 조사 시점, 적용할 부분, 적용하지 않을 부분을 가진다.

에이전트는 다음 결과를 만든다.

- 레퍼런스 카드와 출처
- 페이지 구조와 주요 컴포넌트 목록
- 색상·타이포그래피·간격·반응형 규칙의 디자인 토큰
- 선택한 레퍼런스를 변형한 2개 이하의 시안 방향
- 실제 프로젝트에서 사용할 컴포넌트 매핑

코드 우선 구현에는 shadcn/ui와 같은 소스 소유형 컴포넌트 방식을 우선 검토하고, 편집 가능한 시각 산출물이 필요할 때는 오픈 디자인 도구 어댑터를 추가한다. 상용 사이트의 브랜드·이미지·문구를 그대로 복사하지 않으며, 라이선스가 불명확한 자산은 결과물에 포함하지 않는다.

### 4.7 Coordinator Harness와 검증

Coordinator Harness는 모델이 아니라 모델을 둘러싼 통제 계층이다. 요구사항, 최신 프로젝트 상태, 권한, 작업 할당, 에이전트 이벤트, 검증 결과를 모델 대화와 별도로 저장한다.

각 에이전트 작업은 다음 규칙을 따른다.

1. 현재 상태 버전과 작업 범위를 읽고 작업을 시작한다.
2. 전용 브랜치 또는 작업공간에서 변경한다.
3. 구조화된 handoff와 diff를 기록한다.
4. Coordinator가 충돌과 의존성을 확인한 뒤 통합한다.
5. 통합된 최신 상태에서 검증기를 다시 실행한다.

검증기는 에이전트의 완료 주장에 의존하지 않는다. acceptance criteria에서 테스트·lint·type check·build·브라우저 검증·보안 검사를 실행하고, 명령 출력·diff·스크린샷·버전을 증거로 저장한다. 검증 결과는 `PASS`, `WARN`, `BLOCKED`로 분류하며, 필수 검사가 하나라도 실패하면 통합을 막는다.

## 5. 권한과 안전성

권한은 도구별·작업별로 분리한다.

| 권한 단계 | 기본 정책 | 예시 |
| --- | --- | --- |
| 읽기 | 자동 허용 | 파일 목록, 코드 읽기, 공개 문서 검색 |
| 작업공간 쓰기 | 계획 승인 후 허용 | 프로젝트 파일 생성·수정 |
| 명령 실행 | 명령별 승인 | 테스트, 빌드, 개발 서버 |
| 의존성·네트워크 | 설치 대상과 주소 표시 후 승인 | npm/pip 설치, Git clone |
| 외부 영향 | 항상 별도 승인 | push, 배포, 메일·메시지 전송, 삭제 |

초기 구현은 현재 프로젝트 작업공간 안에서만 파일을 수정한다. 위험한 명령은 allowlist와 금지 패턴을 함께 적용하고, 모든 명령과 결과를 로그로 남긴다. API 키와 비밀번호는 모델 입력과 로그에서 마스킹한다.

## 6. 데이터와 결과물

초기 저장소는 로컬 SQLite와 프로젝트 내 `.oss-builder/` 메타데이터를 사용한다.

주요 엔티티:

- `Project`: 프로젝트 경로, 실행 환경, 기본 권한
- `Request`: 사용자의 원문 요구사항과 구조화된 brief
- `Candidate`: OSS 후보와 조사 근거
- `Decision`: 선정 결과, 점수, 대안, 버전, 라이선스
- `ReferencePack`: 디자인 레퍼런스, 출처, 라이선스, 추출된 토큰과 컴포넌트
- `AgentTask`: 담당 에이전트, 상태 버전, 작업공간, 파일 소유권, handoff
- `VerificationReport`: 실행한 검사, 증거 경로, 결과, 차단 사유
- `Run`: 계획·승인·실행·검증 상태와 로그
- `Artifact`: diff, 테스트 결과, 스크린샷, 결과 보고서

생성 프로젝트에는 다음 파일을 포함한다.

- 의존성 lockfile
- `README` 실행 문서
- `OSS-DECISIONS.md` 선정 근거와 라이선스 목록
- 검증 명령과 결과 요약
- 디자인 레퍼런스 출처와 라이선스 목록
- Reference Pack에서 추출한 디자인 토큰과 컴포넌트 매핑

## 7. 검증 전략

### 기능 검증

- 요구사항이 구조화되는지
- 후보가 최소 2개 이상 비교되는지
- 승인 전 파일·설치 변경이 일어나지 않는지
- 생성·수정된 프로젝트가 지정된 명령으로 빌드되는지
- 테스트와 개발 서버 실행 결과가 사용자에게 전달되는지

### 에이전트 검증

- 명령 실행 권한이 작업공간 밖으로 확장되지 않는지
- 금지된 삭제·외부 전송을 거부하는지
- 테스트 실패 후 제한된 횟수만 재시도하는지
- 실패 시 부분 변경과 복구 방법을 보고하는지

### OSS 선정 검증

- 공식 저장소와 라이선스를 확인하는지
- 버전 또는 커밋이 고정되는지
- 점수만으로 선택하지 않고 근거가 표시되는지
- 선택한 구성의 설치 방법을 재현할 수 있는지

첫 번째 데모의 합격 조건은 하나의 샘플 요구사항으로 작은 웹앱을 생성하고, OSS 후보 비교 → 사용자 승인 → 설치 → 코드 작성 → 테스트·빌드 → 결과 보고의 전체 흐름을 한 번 성공하는 것이다.

## 9. 주요 위험과 대응

### 요구사항 오해

작업 전에 목표·제약·완료 기준을 요약하고, 모호한 부분은 구현 전에 질문한다.

### 잘못된 OSS 선택

후보 비교, 공식 근거, 대안, 라이선스 기록을 필수화하고 사용자가 선택을 승인한다.

### 에이전트의 과도한 변경

Git 기반 작업공간, diff 검토, 단계별 권한, 명령 로그, 제한된 재시도를 적용한다.

### 의존성·공급망 위험

버전을 고정하고, 설치 전 패키지 목록과 출처를 보여주며, 보안 검사와 lockfile 생성을 수행한다.

### 모델 비용과 컨텍스트 증가

단계별 모델 라우팅, 결과 요약, 파일 단위 검색, 컨텍스트 재사용, 작업별 예산을 적용한다.

### 디자인 레퍼런스의 오용

레퍼런스마다 출처와 라이선스를 기록하고, 불명확한 자산은 참고 구조만 추출한다. 원본 브랜드·이미지·문구의 복제를 금지하고, 생성 결과에 적용한 변형을 기록한다.

### 여러 에이전트의 상태 불일치

대화 기록을 공유 상태로 사용하지 않는다. 상태 버전, Git diff, 파일 소유권, handoff, 검증 보고서를 기준으로 삼고, 오래된 상태의 작업은 통합 전에 재기반화하거나 폐기한다.
